# Brief: MCP sub-agent

Zone: `apps/daemon/` except `src/probe.ts` (master). Do not edit anything else.

Goal: one local process that owns the keyboard connection and serves the web UI (HTTP/JSON) and agents (MCP) through the same `KeyboardService`.

## Architecture

```text
Hono on 127.0.0.1:6465
├── /api/*   HTTP/JSON for the UI      (contract: api.ts)
├── /mcp     MCP Streamable HTTP       (contract: tools.ts)
        │
        ▼
KeyboardServiceImpl                    (contract: service.ts)
        │
        ▼
DeviceBackend  ── MockBackend  (in memory, default for tests and dev)
               └─ HidBackend   (Gk6xClient over guardConnection, read-only for now)
```

`DeviceBackend` is internal to the daemon (not a core contract). Suggested shape: `identify()`, `readConfig()`, `writeChanges(changes)`, `close()`. The service never sees a packet. `HidBackend.writeChanges` throws `write-disabled` until the protocol encoders exist and the master enables writes.

Use `@hono/node-server`, `@modelcontextprotocol/sdk` and `zod`, which are already in `package.json`.

## Service rules

Implement every rule in the doc comment of `KeyboardService`. In particular:

- Plans are built in memory, frozen, stored with a TTL (30 minutes) and a cap (100). `listPlans` returns only unapplied, unexpired plans. `plan.baseRevision` is the current `configRevision`.
- `applyPlan` order: check `confirm === true` → check `writeEnabled` → check the plan is not stale → snapshot → write changed records only → read back → compare → return `ApplyResult` with `applied` and `verified` as separate flags.
- A failed verification does not delete the snapshot and does not trigger an automatic restore. It reports the mismatches.
- `restore` snapshots the current state first (`safetySnapshotId`), then writes, reads back and compares.
- Snapshots are JSON files under `profiles/local/<deviceId>/`, written atomically (write to a temp file, then rename). Ids are generated by the server (random UUID). Never build a path from client input. This folder is gitignored.
- `writeEnabled` is true only if all hold: env `PERIFMCP_ALLOW_WRITES=1`, the model is known, and the backend supports writes. Default off. `writeDisabledReasons` lists the failing conditions. Do not set the env var yourself in code, scripts or CI.

## Validation (trust boundary)

Validate every HTTP body and MCP input with zod. The schemas must be assignable both ways to the contract types (add compile-time checks, for example `satisfies z.ZodType<KeysPlanInput>` and the reverse with `z.infer`). Limits:

- colors: `^#[0-9a-fA-F]{6}$`; `speed`, `brightness`: integer 0-100; key ids must exist in the layout; layers from `LAYERS`;
- macros: id and name length limits, at most 256 steps, `delay` 0-60000 ms, `repeat` 1-1000, key codes from `KEY_CODES`;
- `confirm` must be the literal `true`. Anything else is `confirmation-required`.

## HTTP and MCP security

- Bind to `127.0.0.1` only. Port from env, default `DEFAULT_DAEMON_PORT`.
- Reject any request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding). Applies to `/api` and `/mcp`.
- If an `Origin` header is present it must be in the allowlist (default `http://127.0.0.1:5173`, `http://localhost:5173`). No `*` CORS. Otherwise `403 forbidden-origin`.
- `POST` requires `Content-Type: application/json`. Body size limit 256 KB.
- Never log request bodies, serial numbers or snapshot contents.
- Errors use `ApiErrorBody` and `API_ERROR_STATUS`. Do not leak stack traces.
- No route or tool may accept raw bytes, a command number, a file path or a firmware image.

## MCP tools

Register exactly the tools in `ToolContract`, with the names in `tools.ts`. Each one calls one service method. Return `structuredContent` with the typed output plus a short text summary. Service errors become `isError: true` with the `code` and message. `READ_ONLY_TOOLS` and `PLANNING_TOOLS` must work in read-only mode. `WRITE_TOOLS` return `write-disabled` when the service says so. Add a test that fails if a tool is registered that is not in `ToolContract`.

## Known issue to verify (do not test on hardware)

`transport/hidraw.ts` writes the 64-byte packet directly with `node-hid`. The report descriptor of `/dev/hidraw1` has no Report ID (checked read-only: usage page `0xFF00`, usage `0x50`, one 64-byte input and one 64-byte output). `hidapi` expects a leading `0x00` byte on devices without numbered reports, so the transport probably needs to send 65 bytes. Do not change it blindly. Write the fix behind a unit test with a fake `HID` object, flag it in the report, and the master confirms it with the read-only probe.
